# 계획: 보행로 조각을 도시·읍면 모두에서 늘리기 (지도 3단계 ③)

> 2026-10-06 작성. [plan-dong-sections.md](plan-dong-sections.md)의 D3 결과를 이어받는다. 작업 번호 W0, W1 …
> 실행 시간은 이번 세션에서 잰 값 기준이다: **전국 빌드 약 86분** (1차 02:50→04:14, 2차 04:14→05:40), 도로 캐시 읽기 약 4~5분, 표본 6개 시군구 시험 한 번 약 5~10분.

## 지금 얼마나 없나 (2026-10-06 빌드)

| | 개수 |
|---|---:|
| 블록 | 72,795 |
| 보행로로 나뉜 블록 | **4,864 (6.7%)** |
| 보행로 조각 | 18,821 |
| 보행로 파일이 있는 읍면동 | 1,689 / 3,558 (읍·면은 일부러 0) |

도시 동에서도 블록의 한 줌만 나뉜다. 원인은 둘로 본다 (W0에서 숫자로 확인):

1. **OSM 보행로가 면을 못 닫는다.** 인도(`sidewalk`)·횡단보도는 빼고, 나머지 보행로는 대부분 막다른 길이다. 다른 길·보행로와 몇 m 떨어져 끝나거나(연결 누락), 건물 입구에서 끝난다. `cut()`은 막다른 길을 자르지 않는다.
2. **합치기 기준이 크다.** 2,500㎡ · 블록의 10% · 상한 8천㎡라서, 닫힌 면이 생겨도 작으면 이웃에 합쳐진다.
3. 읍·면은 용량 때문에 보행로 단계를 통째로 뺐다 (논밭·산의 `path`가 파일 용량의 약 70%였음).

## 목표 (W0에서 숫자로 다시 확정)

- 도시 동: 8,000㎡ 이상 블록의 **절반 이상**에 보행로 조각이 생긴다 (지금은 전체 블록의 7% 미만).
- 읍·면: 마을(주거·상업 땅)이 있는 곳은 도시와 같은 기준, 논밭·산은 큰 조각으로만 (조각 하나 2만㎡ 이상) — 파일 용량은 읍면 전체의 30% 이하.
- 합쳐서 용량이 정한 예산 안 (아래 결정 1).
- 보행로 파일 한 개(읍면동 하나)가 1MB를 넘지 않는다 (화면 하나 보려고 받는 크기).

## 정할 것 (기본값을 먼저 적어 둠 — 다르면 알려 주세요)

1. **용량 예산**: 지금 107.9MB는 100MB 목표를 이미 넘었다. 보행로를 늘리면 더 커진다. 기본값은 **160MB로 올리기** — 앱이 어차피 지도 데이터를 원격 호스팅으로 옮길 예정이고(`CLAUDE.md` 안드로이드 절), 화면마다 읍면동 파일 하나씩만 받아서 총량보다 *파일 하나의 크기*가 체감에 중요하다. 100MB를 지켜야 하면 W3에서 블록 기준을 올려 상쇄한다 (그만큼 블록이 덜 잘게 나뉨).
2. **보행로 말고 자를 선**: 기본값은 **OSM의 땅 구분 선도 쓴다** — 단지·학교·공원·주차장 등의 경계(`landuse`·`leisure`·`amenity` 면), 철길, 개울·하천, 울타리·담. 건물은 쓰지 않는다 (전국 수천만 개). 원본 `data/korea/south-korea.osm.pbf`가 있어서 추가 다운로드는 없다. 쓰지 않기로 하면 W2를 빼고 W1·W3만 한다 (효과는 W0 숫자로 가늠).

## W0. 안 나뉜 이유를 숫자로 (코드 반영 전) — 약 40분

`scripts/korea-data/audit_walk.py`(읽기 전용)를 새로 만들어 표본 6개 시군구(강남·마포·수원 권선·양평·부안·경주 — 도시 3, 농촌 3)에서:
- 블록 중 보행로가 **하나라도 지나는데** 안 나뉜 블록 수 (→ 이유가 1번).
- 그 보행로 끝점이 다른 길·보행로·블록 경계에서 **3m / 6m / 10m / 20m 안**에 있는 비율 (→ 연결을 이어 주면 몇 개가 닫히나).
- 합치기 기준을 (2,500·10%·8천) → (1,200·5%·4천) → (600·5%·2천)으로 낮췄을 때 늘어나는 조각 수와 JSON 용량.
- 도시·읍면, 블록 면적 구간별로 따로.

산출: `docs/` 표 + 어떤 방법이 몇 %를 해결하는지. 이 표로 W1~W3의 순서를 확정한다. (도로 캐시 한 번 읽는 시간 5분 + 시군구당 1~2분.)

## W1. 끊긴 보행로 이어 붙이기 — 코딩 반나절 + 시험 20분

`build_admin.py`에 `snap_ends(lines, tolerance)`:
- 보행로(`walk` 종류) 끝점이 3~6m 안의 다른 길(블록 도로·보행로·구획 경계)에 닿지 않으면 가장 가까운 점까지 선을 잇는다. 이은 선은 **자를 때만** 쓰고 지도에 그리지 않는다 (만든 선이 아니라 면을 닫아 줄 뿐).
- 허용 거리는 W0 표에서 정한다 (처음 값 5m — 넘으면 잘못 이어서 엉뚱한 곳을 가를 위험).
- 건물 입구로 가는 막다른 길(`footway=entrance`·`access`)은 이어 붙이지 않는다.
- 테스트(`test_admin_blocks.py`): 4m 떨어져 끝난 보행로가 블록을 가른다 / 30m 떨어지면 안 가른다 / 그대로 두면 조각 수가 같다.
- 표본 시군구에서 도시 블록 분할 비율을 다시 잰다 (W0와 같은 스크립트). 이 단계만으로 목표에 못 닿으면 W2로.

## W2. 땅 구분 선으로 더 자르기 (결정 2가 "예"일 때) — 추출 약 40~60분(한 번) + 코딩 반나절

1. **추출**(`scripts/korea-data/extract_boundaries.py`, 한 번만): `south-korea.osm.pbf`에서 pyosmium(이미 설치됨, 4.3.1)으로 태그 필터(`landuse`·`leisure`·`amenity`(학교·병원·주차장)·`natural=water|wood`·`waterway`·`railway`·`barrier=fence|wall|retaining_wall`) → 선(경계)만 `data/korea/boundaries.pkl`에 캐시. 노드 좌표 조회 때문에 전국 한 번에 약 40~60분 예상 — **백그라운드로 먼저 돌리고** 그동안 W1을 한다. 다 끝나면 이후엔 캐시만 읽는다 (약 1분).
2. **쓰기**: 보행로 단계의 자르는 선에 이 경계를 더한다. 경계는 면이라 막다른 길 문제가 없어서 면을 잘 닫는다. 같은 `cut()`·합치기 기준을 쓴다.
3. 블록 경계와 겹치는 선(주거지 경계가 도로를 따라가는 경우)은 이미 블록을 나눈 것이라 `cut()`이 알아서 무시한다.
4. 주의: 하천·철길이 블록을 가로지르면 블록 단계에서 나뉘어야 맞다. 이번엔 **보행로 단계에서만** 쓰고, 블록 단계에 넣을지는 결과를 보고 따로 결정한다 (블록 데이터를 다시 만들면 전국 빌드가 한 번 더 필요).
5. 테스트: 사각 블록 가운데 공원 경계가 있으면 조각이 3개로 나뉨 / 블록 밖 선은 무시.

## W3. 읍·면 보행로 켜기와 용량 조절 — 코딩 2시간 + 시험 30분

- `RURAL` 제외(`build_admin.py`)를 없애고 대신 **읍·면은 더 큰 기준**을 쓴다: 합치기 (10,000㎡ · 10% · 상한 30,000㎡), 단순화는 도시와 같게. 마을(주거·상업 `landuse`)은 도시 기준으로 따로 처리하면 좋지만 W2 결과를 보고 결정 (처음엔 두 기준만).
- 농로 `track`은 계속 뺀다 (논밭이 의미 없이 잘게 나뉘던 원인). 대신 W2의 `landuse=farmland|forest` 경계로 큰 조각만 나뉜다.
- 용량 가드: 읍면동 하나의 보행로 JSON이 1MB를 넘으면 그 동은 기준을 두 배로 올려 다시 자른다 (빌드 스크립트 안에서 자동).
- 도시 기준은 W0 표에서 목표(절반)에 맞는 가장 큰 값으로 정한다.

## W4. 표본 → 전국 빌드 → 검증 — 약 2시간 (거의 대부분 기계 시간)

시간을 아끼려고 전국 빌드를 **한 번만** 하도록 순서를 잡는다.

| 순서 | 작업 | 시간 |
|---|---|---|
| 1 | W2 추출을 백그라운드로 시작 (W0·W1과 병행) | 40~60분 (병행) |
| 2 | W0 점검 → W1 구현·시험 | 약 1.5시간 작업 |
| 3 | W2 쓰기·W3 기준을 표본 6개 시군구로 시험, 기준 값 3~4회 조정 | 회당 약 8분 × 4 |
| 4 | (선택) `--stage walk`: 구획·블록은 다시 안 만들고 보행로 단계만 다시 (아래) | |
| 5 | 전국 빌드 | **약 86분** (보행로만이면 더 짧음) |
| 6 | `validate_admin.py` 전체 + 새 점검(분할 비율·파일 최대 크기) | 약 10분 |
| 7 | 브라우저 확인(0.7m/px 화면, 도시·읍면 각 1곳) | 약 20분 |

**전체 걸리는 시간 추정**: 작업 시간 약 1일 + 기계 시간 약 2.5시간. 기준을 잘못 잡으면 전국 빌드가 86분 더 늘어나므로, 표본 시험에서 *용량 예상치*(표본 × 전국/표본 비율, 이번에 쓴 방식 — 표본 6개 시군구 = 전국의 약 3%)를 보고 정한다.

### 선택: 보행로만 다시 만드는 `--stage walk`

보행로 기준을 바꿀 때마다 86분을 쓰지 않으려고, 첫 전국 빌드 때 구획·블록의 **정확한 도형**을 `data/korea/block-geoms.pkl`에 저장해 둔다 (파일의 단순화된 도형으로 다시 자르면 블록 경계와 어긋남). 이후 `build_admin.py --stage walk`는 이 pkl과 `walk` 파일만 다시 만든다. 효과는 W0에서 단계별 시간을 재서 판단한다 — 보행로 단계가 전체의 절반 미만이면 이득이 작아서 만들지 않는다. pkl은 수 GB가 될 수 있어(블록 72,795개 정확한 도형) 크기도 같이 본다.

## W5. 앱·문서

- 앱 코드는 원칙적으로 변경 없음: 보행로 파일이 없으면 블록 그대로 그린다 (`StaticAdminAreaService`). 읍·면에도 파일이 생기므로 `adminAreaService.test.ts`에 "읍·면 코드에서도 walk 파일을 요청한다" 한 줄만 확인한다 (지금도 지역으로 구분하지 않으면 테스트 불필요).
- 0.7m/px에서 작은 조각(2,500㎡ 안팎, 지름 50~60px)이 반지름·간격 때문에 지워지지 않는지 확인 (`areaRenderer`). 지워지면 `'block'` 단계에서만 반지름 상한을 낮춘다 — 이건 앱 변경이라 별도 작업.
- `scripts/korea-data/README.md`·`CLAUDE.md` 지도 바탕 절에서 "읍·면이면 블록 그대로"를 고치고, 새 기준·용량·`extract_boundaries.py`·`audit_walk.py` 설명을 더한다. 이 문서 맨 아래에 결과를 적는다.

## 위험

- **잘못 이은 선**: 끝점을 이을 때 가까운 엉뚱한 길로 가면 블록이 이상하게 갈린다. 허용 거리를 작게(5m) 시작하고, 이은 선이 건물 사이·통로를 가르는 예를 `area-preview`(출력 폴더 오류를 먼저 고칠 것)로 눈으로 본다.
- **추출 시간 초과**: PBF 전체 추출이 예상보다 길면 도시가 많은 시도(서울·경기·부산·인천 등)부터 먼저 하고, 나머지는 W3 기준으로만 한다.
- **용량**: 조각 수가 늘면 JSON이 커진다. 읍면동별 1MB 가드와 전국 예산(결정 1)을 같이 지킨다.
- **무한히 나뉨**: 합치기 기준 아래로는 안 내려가므로 조각 수는 `면적 / 기준`으로 위에서 막힌다 — 그래도 도시 동 하나의 보행로 JSON이 1MB를 넘는지는 W4 6번에서 확인.

W0 → (W2 추출 병행 시작) → W1 → W2 쓰기 → W3 → 표본 조정 → 전국 빌드 1회 → 검증 → W5. 각 단계 끝에서 `python scripts/korea-data/test_admin_blocks.py`와 `npm run check`를 통과시킨다.

## 결과 (2026-10-06, 완료)

- **W0** (표본 6개 시군구, 블록 2,220개): 보행로가 20m 넘게 지나는 블록은 도시 46%, 그중 실제로 나뉜 것은 15%. 보행로 끝점이 3m·6m·10m·20m 안에 다른 길이 있는 비율은 도시 4%·10%·16%·35%, 20m 밖(진짜 막다른 길)이 39%. 합치기 기준을 낮추는 것(2,500 → 600㎡)은 160 → 237개로 느는 정도였다.
- **W1 (끊긴 보행로 잇기)**: 5m 안에서 이어도 160 → 161개, 시간만 3배(24초 → 78초) → **껐다** (`WALK_SNAP_M = 0`, 코드와 테스트는 남김).
- **W2 (땅 구분 선)**: 도시 블록 분할 160 → 549개(52%). 추출은 PBF 288MB에서 약 1분(예상 40~60분보다 훨씬 빠름), 47만 개 선. 긴 선을 30꼭짓점씩 토막 내고(`chunk_lines`) 보행로 단계에서 병합 뒤 재자르기를 끄자(`recut=False`) 속도가 약 2배로 빨라졌다.
- **W3 (읍·면)**: 하천·철길·울타리만 + 3만㎡ 기준 → 표본에서 블록 1,161개 중 171개 분할, 파일 1.4MB(논밭·산 둘레까지 쓰면 259개 · 2.3MB). 읍·면 단순화는 4e-5.
- **전국 빌드**: 보행로 조각 18,821 → **99,254**개, 보행로 파일 3,514개(읍면동 3,558개 중; 중앙값 16KB, 최대 856KB), 합계 **183.4MB**. `validate_admin.py` 문제 0건.
- **브라우저 확인**: 강남 역삼1동 0.38m/px에서 보행로 조각이 흰 경계로 그려지고 콘솔 오류 없음. 0.7m/px 근처에서 반지름·간격이 작은 조각을 지우는지는 아직 눈으로 안 봄.
- **남은 것**: 용량이 목표(160MB)보다 크다. 줄이려면 합치기 기준을 올리고 다시 빌드(약 2시간).

## 도로 단계 (2026-10-06, "모든 도로가 보이도록")

용량 제한 없이, 닫힌 면을 못 만드는 도로(막다른 길·진입로·인도 등)도 보이게 하려고 보행로 단계 아래에 한 단계를 더했다.
- 방식: 보행로 단계에서 보이는 조각(leaf)마다 모든 highway의 양옆 0.4m를 파낸다 (`build_roads.py`). 면을 닫는 길은 갈라지고 막다른 길은 홈으로 남는다. 닫힌 면만 세던 방식(`cut()`)으로는 보이지 않던 길이 모두 틈이 된다.
- 앱: `focusLevel`에 `'road'`(0.3m/px 미만), `StaticAdminAreaService`가 `road/<시군구>/<읍면동>.json`을 받아 가운데 조각을 쪼갬(없으면 보행로 단계), 코드 패턴 `(-\d{1,4}){0,4}`.
- 결과: 1,263,585조각, 1,109MB(중앙값 249KB, 최대 3.7MB), `validate_admin.py` 문제 0건, `npm run check` 320개 통과. 강남 역삼1동 0.27m/px 확인: 도로가 틈으로 보이고 콘솔 오류 없음. 홈이 눈에 띄는 곳을 따로 찾아 보진 않았다.
- 남은 것: 모바일에서 큰 파일(3.7MB) 읽기 시간, 원격 호스팅 전환(APK에는 못 넣음).
