# 계획: 동 내부를 큰 도로 → 작은 도로 → 전체 도로 순으로 빠짐없이 나누기

> 2026-10-06 작성. [plan-area-blocks.md](plan-area-blocks.md)(B0~B5)의 뒤를 잇는다. 작업 번호는 D0, D1 …

## 풀려는 것

지금 동 안쪽은 `build_admin.py`의 `sections()`가 **큰 도로로 한 번, 남은 큰 조각만 작은 도로로 한 번** 자른 뒤(`SPLIT_ABOVE_M2`·합치기 기준 때문에 곳에 따라 덜 나뉜다), 블록·보행로 조각이 따로 이어서 자른다.
단계가 도로 종류가 아니라 *조각 크기* 규칙으로 섞여 있어서:

- 같은 동 안에서도 어떤 곳은 작은 도로까지 나뉘고 어떤 곳은 큰 도로 조각 그대로다 (150,000㎡ 미만 조각은 작은 도로를 안 씀).
- 블록 단계(`BLOCK_SKIP_BELOW_M2` 3만㎡), 보행로 단계(3천㎡·"나뉜 블록만 저장")도 건너뛰는 조각이 있다.
- 단계마다 어느 도로로 잘랐는지 한마디로 설명이 안 된다.

**목표:** 동 하나를 도로 등급 순서대로 **세 단계로, 단계마다 동 전체를 빈틈없이** 나눈다. 앞 단계의 조각을 다음 단계가 더 잘게 쪼개는 포함 관계(트리)를 지킨다.

| 단계 | 자르는 도로 | 화면 축척(기존 단계에 맞춤) | 데이터 |
|---|---|---|---|
| ① 큰 도로 | `motorway`·`trunk`·`primary`·`secondary`·`tertiary` (+ `_link`) | 8m/px 미만 | `section/` |
| ② 작은 도로 | ① + `unclassified`·`residential`·`living_street`·차가 다니는 `service` (주차장 통로·진입로 제외) | 2m/px 미만 | `block/` |
| ③ 전체 | ② + `footway`·`path`·`pedestrian`·`steps`·`cycleway`·`track` + 주차장 통로·진입로 (인도·횡단보도·실내·터널은 제외 — 띠만 생김) | 0.7m/px 미만 | `walk/` |

파일 위치·코드 형식(`<동>-<①>-<②>-<③>`)과 `focusLevel` 문턱은 B2에서 만든 것을 그대로 쓴다. 바뀌는 건 **데이터를 자르는 규칙**과 그 규칙이 빈틈 없는지 검증하는 부분이다.

## 정해 둔 가정 (다르면 알려 주세요)

1. "구획"은 지금 세 단계(구획·블록·보행로 조각)를 통틀어 부르는 말로 보았다. 단계 이름·파일 경로는 바꾸지 않는다 (옛 배포·코드 호환).
2. "전부"는 **모든 동(읍·면 포함)의 모든 조각이 해당 단계까지 나뉜다**는 뜻이다. 곳에 따라 건너뛰지 않는다. 도로가 없어서 안 나뉘는 조각만 그대로 한 조각.
3. 너무 작은 조각(슬리버)을 이웃에 합치는 건 유지하되 기준만 낮춘다 (화면에서 보이지도 않는 틈이 목적이 아니다).

## D0. 지금 상태를 숫자로 재기 (코드 반영 전)

`scripts/korea-data/`에 읽기 전용 점검 스크립트를 둔다 (`audit_admin_levels.py`).
- 동마다: 큰 도로로만 자른 조각 수, 작은 도로까지 자른 조각 수, 전체까지 자른 조각 수, 각 단계 중간 면적·최대 면적.
- "덜 나뉜 곳" 목록: ①이 지금 `SPLIT_ABOVE_M2`·`BLOCK_SKIP_BELOW_M2`·`WALK_SKIP_BELOW_M2` 때문에 건너뛴 조각 수와 그 면적 비율.
- 강남구·마포구·수원 권선구·양평군(B0와 같은 4곳)에서 먼저 돌려 기록한다. 이 표가 이후 단계의 비교 기준(전·후).

## D1. 데이터: ① 큰 도로 단계를 동 전체에 적용

- `sections()`를 `main`만 쓰도록 단순화한다: `cut(dong, main, min)` 한 번. `SPLIT_ABOVE_M2`·`LOCAL_MIN`·`local` 두 번째 패스를 지운다 (작은 도로는 ②의 몫).
- 합치기 기준 `MAIN_MIN`은 D0 결과로 정한다 (출발점: 15,000㎡ 또는 동 면적의 1%). 도로가 하나도 안 지나는 동은 조각 하나.
- `section_roads()` 캐시에서 `local` 도로를 뺀다 → 캐시 형식이 바뀌니 파일 이름에 버전을 붙여 다시 만든다 (`section-roads-v2.pkl`).
- ⚠ 구획 파일이 지금보다 **조금 더 커지거나 조각 수가 늘 수 있다** (옛 ①은 큰 조각을 작은 도로로 이미 쪼갰다). D0의 크기와 비교해서 확인.

## D2. 데이터: ② 작은 도로 단계를 모든 ① 조각에 적용

- `split(section, block, BLOCK_SKIP_BELOW_M2, BLOCK_MIN)` → **건너뛰기를 없앤다.** 3만㎡ 미만 조각도 작은 도로가 지나가면 자른다 (안 지나가면 자연히 한 조각).
- 자르는 길 = `BLOCK_HIGHWAYS` − `MINOR_SERVICE` (지금과 같음) + ①에 쓴 큰 도로(이미 ① 경계라서 중복이지만 `polygonize`가 처리).
- 합치기 기준 `BLOCK_MIN`을 도시 블록이 사라지지 않게 낮춘다 (출발점: 2,500㎡ 또는 조각의 5%). 너무 낮으면 주차장 통로가 만든 슬리버가 남는다 — D0의 "아주 작은 조각 비율"로 확인.
- 도로 위 한가운데를 지나는 선(막다른 길)은 `cut()`이 이미 무시한다.

## D3. 데이터: ③ 전체 단계를 모든 ② 조각에 적용 (저장 범위 결정이 핵심)

지금 보행로 파일에는 **나뉜 블록의 조각만** 저장한다(안 나뉘면 블록 화면을 그대로 둠). "전부 진행"과 파일 크기가 부딪히는 부분이라 둘 중 고른다:

| 안 | 내용 | 크기 영향 |
|---|---|---|
| **A (추천)** | 지금처럼 **나뉜 조각만 저장**. 대신 건너뛰기(`WALK_SKIP_BELOW_M2` 3천㎡)를 없애고 합치기 기준을 800㎡ → 400㎡로 낮춤. 안 나뉜 조각은 정말 보행로가 닫히지 않는 곳이라는 뜻 | 현재 13MB에서 소폭 증가 예상 |
| B | 모든 ② 조각을 저장 (안 나뉜 것도 조각 하나로) | 블록 단계와 같은 도형이 중복 → 약 +50MB, 100MB 한도 초과 |

A로 간다. 앱은 이미 "조각이 없으면 위 단계를 그대로 그림"을 처리한다 (`StaticAdminAreaService`).
- 자르는 길에 `footway=sidewalk|crossing`은 계속 뺀다. `track`(농로)은 [B1b 결정](plan-area-blocks.md#b1·b1b-결과-2026-10-05-완료) 그대로 뺀다 — 논밭이 의미 없이 잘게 나뉨.
- 도시 동은 이 단계에서 거의 안 나뉜다는 B0 결과가 있다(8%). 400㎡로 낮췄을 때 늘어나는 비율을 D0 표로 확인하고, 여전히 낮으면 **그 자체가 한계임을 문서에 적는다** (OSM에 보행로가 닫히지 않음).

## D4. 검증 (`validate.py`·`test_admin_blocks.py`)

세 단계 모두 같은 검사:
- 한 동의 조각을 모두 합치면 그 동과 같다 (빈틈·겹침 ≤ 0.2%, 섬은 따로 남김).
- 다음 단계 조각의 코드 접두사가 이전 단계 조각이고, 합치면 그 조각과 같다 (트리).
- **건너뛴 조각 수 = 0**: 작은 도로(또는 보행로)가 조각을 지나가는데도 한 조각으로 남은 경우가 없다. 이 검사가 "전부 진행"의 증거다.
- 조각 수가 하나인 동 목록을 출력 (도로가 정말 없는 곳인지 눈으로 확인).
- 회귀: B0의 4개 시군구에서 D0 대비 조각 수·파일 크기 표를 `docs/`에 남긴다.

## D5. 앱 쪽 확인 (코드 변경은 최소)

- `adminAreas.ts`·`adminAreaService.ts`는 단계·파일 구조가 같아서 **원칙적으로 변경 없음**. 확인만: 코드 정규식(`^\d{1,10}(-\d{1,3}){0,3}$`)의 번호 3자리 한도가 새 조각 수(한 동에 ①②③ 각각 999개 이하)를 넘지 않는지 `validate.py`에서 최댓값을 본다. 넘으면 한도를 4자리로 올리고 옛 코드도 계속 읽히게 한다.
- `areaRenderer`의 반지름·간격이 더 작아진 조각을 지우지 않는지 `area-preview`로 역삼1동·신사동에서 본다 (B3 항목 재확인).
- 단계별 확대(8m/px → 2m/px → 0.7m/px)에서 가운데 범위(`alsoFocus` 최대 4개)에 걸친 조각이 **전부** 다음 단계로 나뉘는지 모바일(375px)에서 확인, `npm run shots`에 한 장 추가.

## D6. 배포·문서

- 용량: 전국 합계가 100MB 안인지 확인 (현재 96.7MB). 넘으면 D3의 합치기 기준을 올리거나 읍·면의 ③을 뺀다 (B의 결정 3 그대로).
- `scripts/korea-data/README.md` 표에 세 단계 자르는 도로 규칙을 이 문서 표대로 갱신.
- `CLAUDE.md` 지도 바탕 설명을 "큰 도로 → 작은 도로 → 전체 도로, 단계마다 동 전체를 빈틈없이"로 한 줄 고침.
- `public/korea/admin`은 Git에 없으니 새로 만든 데이터를 배포에 따로 넣는다.

## 순서와 중단점

D0 → D1 → (검증) → D2 → (검증) → D3 → (검증) → D5 → D6. 한 단계 끝날 때마다 `validate.py`와 `npm run check`를 통과시키고, D1·D2는 데이터만 바뀌므로 각각 4개 시군구에서 먼저 확인한 뒤 전국으로 돌린다 (전국 빌드는 수십 분 — 도로 캐시를 재사용).

## 열린 질문

1. **용어**: "구획"이 지금 이름(구획·블록·보행로 조각) 전체를 뜻하는 게 맞는지, 아니면 *구획 단계(①)만* 더 잘게 나누라는 뜻인지. 후자라면 D2·D3이 아니라 ①만 큰 → 작은 → 전체 세 패스로 나누고 블록·보행로 단계는 건드리지 않는다.
2. D3은 A(나뉜 것만 저장)로 가도 되는지.
3. 읍·면(농촌)도 ②·③까지 똑같이 적용하는지 (기본: 예, 100MB 안에서).

## 결과 (2026-10-06, D0~D6 완료)

**D0 (4개 시군구, 옛 규칙)**: 아직 더 잘리는 조각이 구획 6·7·3·0개, 블록 2·2·3·0개 (마포·강남·권선·양평). 건너뛰기 규칙 때문.

**실제로 한 것**
- `build_admin.py`: 구획은 큰 도로만(`sections`), 블록·보행로 조각의 크기 건너뛰기 삭제. 합치기 기준에 상한 추가(`merge_min`). 합쳐서 막다른 길이 닫힌 조각은 한 번 더 자름(`cut`의 `depth`). 읍면동 전체 분할은 `dong_tree`.
- 새 규칙 점검: 아직 더 잘리는 조각이 4개 시군구 합쳐 구획 2개·블록 2개·보행로 5개 이하로 줄었다 (남은 건 재자르기 깊이 2의 한계).
- 테스트: `test_admin_blocks.py` 9→10개 (작은 구획도 자름, 작은 블록에 보행로, 단계별 완전 분할·코드 포함 관계, 읍·면 보행로 없음).
- `validate_admin.py`: 전국 **문제 0건** (포함 관계, 블록이 구획을 덮음, 번호 999 이하). 읍면동 3,558개 중 한 조각으로 남은 곳 53곳 (도로가 없는 섬·작은 동).

**D3 결정 (A안 + 읍·면 제외)**
- 첫 빌드는 합치기 기준을 낮췄더니 227.6MB (블록 12.7만, 보행로 7.3만 조각 — 보행로 98MB). 100MB를 크게 넘어서 표본 6개 시군구로 기준·단순화를 바꿔 가며 쟀다.
- 최종: 블록 기준 8천㎡·10%·상한 5만㎡, 보행로 2,500㎡·10%·상한 8천㎡, 단순화 구획 7e-5 · 블록 3e-5 · 보행로 1.5e-5(소수점 5자리), **읍·면은 보행로 단계 없음**(논밭·산 보행로가 보행로 용량의 약 70%).
- 합계 **107.9MB** (구획 22 · 블록 65 · 보행로 21 · 읍면동 8). 100MB 목표를 약 8% 넘는다 — 줄이려면 블록 기준을 더 올린다.
- 전국 조각 수: 구획 25,561 · 블록 72,795 · 보행로 18,821. 옛 규칙은 구획 24,225 · 블록 54,107 · 보행로 9,868.
